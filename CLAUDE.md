## Commands

```bash
# Build (debug)
cargo build

# Build (optimized — fat LTO, single codegen unit)
cargo build --release

# Run
cargo run [--release]

# Bench
cargo bench --bench lstm_training
cargo bench --bench hierarchical_training   # set RAYON_NUM_THREADS=1 for a serial reference

# Check without producing a binary
cargo check
```

The binary reads one line from stdin to select its mode:

| Input | Action |
|-------|--------|
| `h` | `train_hierarchical` — trains the three-part hierarchical model on the CPU (`cpu::hierarchical`, v2 checkpoints); the `hg` loop without audio and without carrying state across windows |
| `hg` | `train_hierarchical_gpu` — same model, trained on the GPU (needs `--features cuda`); writes v2 checkpoints (`src/checkpoint.rs`) |
| `hga` | the audio stage, after text pretraining: the `hg` loop with an audio window (a LibriSpeech run read as text with some utterances heard through `<model>.ae2`, or, for `AUDIO_PRETRAIN_VOICE_P` of them, a pretraining-holdout document the voice takes were read out of, those takes heard where their sentences stand) after every `AUDIO_PRETRAIN_EVERY` text windows, backbone at the constant `AUDIO_STAGE_LR`. Trains `<model>_audio`, copied from `<model>` on the first run, so the text model is never written. `hg` itself never runs audio |
| `hq` | `train_sft` — CPU Q-A / instruction fine-tuning on `SFT_DATA`, loss masked to the response. The CPU twin of `hqg` |
| `hqg` | `train_sft_gpu` — GPU Q-A / instruction fine-tuning on `SFT_DATA`, loss masked to the response (needs `--features cuda`). |
| `hv` | `validate_hierarchical` — forward-only pass over `VAL_DATA` (CPU), reporting mean char and word loss; no backward, no weight update |
| `hvg` | `validate_hierarchical_gpu` — the same validation on the GPU (needs `--features cuda`), through `Hierarchical::eval_loss`: forward only, no gradient, no step, backbone offload turned off. ~2.2-2.4x a training window (`examples/eval_win.rs`) |
| `hs` | `sample_hierarchical` — interactive sampling from the hierarchical model (`src/infer.rs`, v2 checkpoints) |
| `hqs` | `sample_chat` — interactive Q-A sampling from an SFT model (prompts for an instruction + optional context, generates the response until `<END>`) |
| `i` | `inspect_model` — prompts for a model name, looks it up in `models/` and prints its structure: for a v2 checkpoint the widths, every block's cell, the parameter count and how many chars/words it has trained on (pretraining and SFT counted separately); for a flat `Sequential` file every layer with its settings |

## Style 

do not use `0.0_f32`, always prever the simple mumber: `0.0`
All comments need to be in englisch not in german

Comments describe the code, not the edit. Never write a comment about what you
changed, added, moved, or why you changed it — no "was X, now Y", no "kept for
compatibility", no "moved here from foo.rs", no "NEW:". That belongs in the commit
message or the chat, not in the file: the next reader has no idea what the previous
version looked like and does not care.

Keep comments short. Only comment what is not immediately understandable from the
code — a non-obvious invariant, a unit, a reason the naive approach fails, a
reference to a paper or reference implementation. Do not restate what the line
already says, and do not write a paragraph where a line does.

No banner or separator lines in comments: no `// =====`, no `// -----`, no boxed
headers. They add lines without adding information and make the file look more
verbose than it is. A section heading is one plain comment line.

## Architecture

### Checkpoints (`src/checkpoint.rs`)

Format v2: a header (`ModelCfg` widths, a `Layout` with every block's `BlockKind` as a one-byte tag plus u64 arguments, step, `Seen`), then every parameter tensor in `param_slots` order as rank + dims + raw f32, in the GPU layouts (fused projections, the 1/√dqk folded into the mLSTM's `wk`/`bk`). A new cell type is a new tag. The GPU model writes and reads it straight from the device, `src/infer.rs` (sampling, `harness`) reads it, and so does the CPU model `cpu::hierarchical` (`h`, `hq`, `hv`), which converts on load and save: the sLSTM's four `[in+H, H]` gate matrices, the unfused mLSTM projections, `wk`/`bk` unscaled. `examples/gpu_cpu_parity.rs` checks the CPU model's loss against the GPU's on a real checkpoint (s4.v2: 0.018%).

### Hierarchical model (`src/cpu/`, `src/gpu/`, `src/infer.rs`)

`Hierarchical` (HAT-style, arXiv 2501.10322) couples three stages, over a window of words, phase by phase (all encodes, then the backbone sweep, then all decodes):

- **encoder** — the tied char table and alternating sLSTM/mLSTM blocks over the characters of one word plus a closing `[W]` end-of-word step (fed virtually — token slices never contain it); the word embedding `e_w` is the output at the `[W]` step, where the state has seen the whole word and knows it is complete. State is reset per word.
- **backbone** — `Linear → mLSTM blocks × WORD_BLOCKS → Linear` (s4/s5 also carry sLSTM blocks; the checkpoint's `Layout` records every block's cell) — autoregresses over word embeddings, carrying recurrent state across words; its output is the context for decoding the *next* word.
- **decoder** — `blocks → RMSNorm → head → SoftCap`, with no front layer: a word's **first sequence step is the injected backbone context** (it takes the BOS slot, paper eq. 3–4), every later step feeds the previous char through the **encoder's char table** (tied; requires CHAR_HIDDEN == OUT_HIDDEN). Predicts the word's chars plus a trailing `[W]` (EOS). Reset per word.

There are three implementations of it. `gpu::Hierarchical` trains (`hg`, `hqg`, `hvg`). `cpu::Hierarchical` (`src/cpu/`, batched `[B, T, F]` layers on `crate::tensor`, hand-written backward) is the CPU twin (`h`, `hq`, `hv`) and the GPU's parity reference and init source; it runs the encoder and decoder per group of equal-length words, at most `GROUP_MAX_ROWS` rows at once. `infer::Hierarchical` is forward-only with no training state, steps one position at a time and is what `hs`, `hqs` and `harness` run.

Optimizer assignment convention: interior projections are weight-decayed; embedding tables and the logit head train without decay — putting hidden projections on the undecayed path causes unbounded weight growth over long runs. The decoder's logit head is additionally followed by `SoftCap` (`LOGIT_SOFTCAP = 30` like xLSTM-7B): `logits = cap·tanh(z/cap)` bounds the logits so the undecayed head has no incentive to grow without limit.

Words come from `src/segment.rs` (see Tokenizer below), not from a boundary-token set.

### Sequential (`src/sequential/`)

A flat per-timestep layer stack (`Sequential`, assembled by `SequentialBuilder`), used by `smart-light`'s wake-word detector. Every layer implements `NnLayer` and owns its weights **and** its gradient accumulators; `DynCache` is a type-erased per-timestep forward cache each layer downcasts in `backward`. The layers (`layers/`: linear, no-bias linear, embedding, SiLU dense, LSTM, sLSTM, RMSNorm, causal conv1d, dropout, soft cap) step themselves on per-tensor Adam with decoupled decay (`optim.rs`). The file format (`io.rs`) is the `NNM1` container (kind 0, one `"model"` section holding an `NNFW` stack blob); a hierarchical `NNM1` (kind 1) is refused.

### Optimizer

The CPU model steps AdamW per layer (`cpu::optim`, a shared `AdamCfg`). `BATCH_SIZE` in `config.rs` accumulates gradients over that many windows before each optimizer step.

The GPU path runs AdamW out of a **parameter arena** (`src/gpu/arena.rs`): every parameter, gradient and AdamW moment lives in one of a few contiguous allocations laid out identically, and each layer holds windows (non-owning `DTensor`s) into them. A step is therefore one `adamw_arena_q8` launch plus one memset over the gradients per arena instead of ~900 of each, and every weight keeps a fixed device address — the prerequisite for capturing a step in a CUDA graph. The hierarchical model binds **three** arenas, one per stage (encoder incl. the tied char table, backbone, decoder), because the arena step takes a single `AdamCfg` for the range it covers and the stages do not want the same one: under Adam a step moves each parameter by about `lr` whatever the gradient was, so what it does to a layer's *output* grows with fan-in, and one rate across a `WORD_HIDDEN`-wide backbone and `CHAR_HIDDEN`-wide character stacks trains the narrow ones at a fraction of the rate their width asks for (`ENCODER_LR_SCALE` / `DECODER_LR_SCALE`, both `1.0` = the single-rate behaviour every existing checkpoint trained under; μP's `lr ∝ 1/fan_in` puts them at `WORD_HIDDEN / CHAR_HIDDEN`). The split is also what makes the per-stack `*_WEIGHT_DECAY` constants reach the GPU path — a single arena had one `weight_decay`, so the encoder's and decoder's were read by the CPU trainer alone. `Hierarchical::param_slots_by_stage` is the enumeration the arenas bind; `param_slots` is it flattened, in the same order as before. Each layer enumerates its tensors exactly once, in `param_slots`, tagging each with a `ParamKind` (`Decay` / `NoDecay` / `Frozen`); the arena packs them in that order so the decay term and the extent of the update are bound checks on the element index. `params_mut` (checkpointing) and `grads` (diagnostics) are derived from the same enumeration, and a standalone layer or a parity test steps its own slots eagerly through `arena::step_slots`. A layer never allocates what the arena is about to give it storage for: `m`/`v` are built as `arena::unbacked` (an empty tensor) and `bind` releases the layer's own gradient before it allocates anything, so **`bind` carries the parameters across and hands back gradients and moments at their zero init** — the state they are in at construction and after every step. `step_slots` materializes the moments on the first step of a layer used on its own, and a test that wants a seeded gradient writes it through the arena's buffer after binding. This is where the process peaks, and at 584M parameters the four fp32 copies of the model that used to be alive across `bind` were what made a 16 GB card OOM at startup before the first window.

The two moments are held in **8 bits** (Dettmers et al., arXiv 2110.02861): one byte per parameter, an index into a 256-entry map of magnitudes normalized to the absmax of its `QBLOCK` = 2048-element range, plus one fp32 scale per range — 2 bytes per parameter against fp32's 8. At 465M parameters that is 886 MB instead of 3552 MB, the largest single block of device memory in the process after the activations, and it is what the arena step's bandwidth is spent on. Only the state *carried between* steps is quantized: `adamw_arena_q8` dequantizes into registers, computes the update in fp32 and re-quantizes against the range's new absmax — which is why the kernel is one CUDA block per range (the new absmax is a block-wide reduction) rather than one thread per element. The map is non-uniform, fine near the absmax and coarse seven decades below it, because `v` enters as `1/sqrt(v)` and an element flushed to zero would step without bound. There is no fp32 moment path: the reference the quantized step is tested against is `step_slots`, the per-tensor fp32 AdamW (`q8_moments_track_the_fp32_reference` measures 0.9% rms drift over a 20-step run against it; per element and per step the map costs up to ~5% of an update, which is what the arena's own step tests tolerate). Frozen parameters carry no moment at all.

### Saved activations and offload (`src/gpu/offload.rs`)

Everything a GPU block's backward reads — its FFN activations, its norms' `inv_rms`, its cell's whole cache (the mLSTM's `q‖k‖v‖o` slab, gate logits, `MlstmFused` chunk states, `yhat`; the sLSTM's gate buffer and slabs), and its pre-norm output, written bf16 and read by either cell as its GEMM input — lives in one **`Frame`**: a byte range each layer carves typed views out of with a `carve(frame, b, t)` function that forward and backward both call, so the layout cannot drift and no layer holds a saved tensor of its own. `Frame::measure()` sizes a layout without memory. A block's frame is one contiguous range, so offloading it is one D2H and one H2D. What is cheaper to recompute than to move is not saved: `SiLU(gate_pre)` (redone inside `swiglu_backward`), the mLSTM's `σ(o)⊙yhat` (one `ogate_fwd` in backward), and the cell output of a cell that does not read it (`Cell::NEEDS_Y`, false for the mLSTM). An offloaded block also drops the FFN's `gate_pre`, `value` and `mixed` and rebuilds them from `norm2_out` in backward (`Block::recompute_ffn`, set by `set_offload`): two GEMMs against ~35 MB of PCIe per frame, which took the backbone frame from 86 to 51 MB and a 4096-word window at WORD_HIDDEN 1280 / 48 blocks from 0.807 to 0.630 s. Resident blocks keep saving them, since there the copy costs nothing. `FrameStack` hands frames out: **resident** (`ResidentFrames`, one reusable device buffer per stack depth — encoder, decoder, eval, `GPU_NO_OFFLOAD`) or **offloaded** (`Offload`, the backbone only). The backbone forwards chunk-major and unwinds in exact reverse, so all its blocks' frames form one LIFO: one `Offload` shared by every backbone block holds a pinned host stack (sized per window by `Hierarchical::reserve_offload` from the spans, with 1/16 headroom so a slightly larger window does not re-pin ~10 GB) and a fixed ring of `RING_SLOTS = 3` device slots sized at construction for the largest frame of a `BACKBONE_CHUNK` chunk. Ordering is one event per slot that the compute stream waits on before writing or reading it — nothing is allocated or freed per frame. The ring is a write-through cache: every frame goes to the host as its forward ends, a pop prefetches the two frames below it, and frames still in a slot at the forward/backward turnaround come back without a copy. At 4096 words this holds 1.46 GB of activations against 3.6 GB for the per-layer parks it replaced. The forward is close to PCIe-bound — a ~32 MB mLSTM frame copies in about the time its block computes — so bytes per frame are step time: at ~42 MB the same design ran 15% slower.

### Tokenizer and word segmentation (`wordseg/`)

The byte tokenizer and the word split live in their own dependency-free workspace crate, because both sides of the pipeline must agree on them byte for byte: the model trains on words, and `datamix` caps a corpus in the same words the trainer will see. `neural-networks` re-exports both modules (`pub use wordseg::{segment, tokenizer_utf8}`), so `crate::segment::…` and `crate::tokenizer_utf8::…` still resolve everywhere inside it, and `MAX_WORD_BYTES` now lives with the splitter it defines (re-exported from `config`).


`Utf8Tokenizer` (`wordseg/src/tokenizer_utf8.rs`) is byte-level: ids `0..256` are raw UTF-8 bytes, ids `256..` are the specials in `SPECIAL_TOKENS` (`<W>` = end-of-word marker, `<END>`, plus the SFT markers below), so `vocab_size() == 256 + SPECIAL_TOKENS.len()` (266; a pretraining-only model uses just the first two). Any UTF-8 text round-trips losslessly and no input byte can collide with a special. There is no charset file. Sampling decodes with `Utf8Printer` (`src/sampling.rs`), which holds bytes back until they form a whole character.

`segment::word_ends` (`wordseg/src/segment.rs`) decides what a "word" is — the unit the backbone autoregresses over — with a lexer-shaped split tuned for Rust: a whitespace run is one unit and attaches as a *suffix* to the word before it (`"use "`, `";\n    "`), so a word carries the separator that closes it and the decoder emits that separator right before `[W]`; identifiers/keywords and numbers stay whole (`foo`, `1_000u32`), multi-byte operators are one word (`::`, `->`, `..=`, `//`), lifetimes (`'a`) differ from char literals (`'a'`), and non-ASCII bytes group into their character. Words tile the sequence contiguously and are capped at `MAX_WORD_BYTES` (config), which bounds the decoder unroll. Roughly 3–4 bytes per word on Rust source. `cargo run --example seg_demo -- src/foo.rs` prints the split for a file.

### Post-training / SFT (`src/sft.rs`, `src/gpu/train.rs`)

Q-A instruction tuning of a pretrained hierarchical model, GPU only. Three pieces:

- **Chat special tokens.** `SPECIAL_TOKENS` gains, *after* the pretraining `<W>`/`<END>` so no existing byte/`<W>`/`<END>` id ever shifts: the structural markers `<CONTEXT>` (258) and `<SEP>` (259), then the **markup** markers `<tool>`/`</tool>` (260/261), `<result>`/`</result>` (262/263) and `<think>`/`</think>` (264/265). `vocab_size()` is therefore 266, while a pretrained checkpoint has 258 (`PRETRAIN_SPECIALS`). Markup differs from the structural markers in that it also occurs verbatim in the data: `to_tokens_markup` folds each literal occurrence into its token, `to_text_markup` writes it back out, and `MARKUP_START` is where the markup range begins. `ChunkedWordDataSet` tokenizes pretraining documents through it too, so a literal `<tool>` in a web page or a source file is the same one token there as in an SFT window — measured on the shipped corpus that is ~270 occurrences in 34.4G tokens, so the point is one representation everywhere, not volume. A call boundary is therefore one token the model either emits or does not, instead of a spelling it can get subtly wrong, and `sample_chat` detects a call by the `<tool>` **token** rather than by a substring. What sits *between* the markers is still plain text, so the call syntax itself stays a convention of the data alone (`mixes/synth/*.syn`) and a new protocol costs no vocab entry. A **tool result** still needs no role marker: `Role::Tool` renders as `<result>…</result>` followed by `<SEP>`, so it sits on the prompt side exactly like a user turn and the reply after it is what carries loss. The pretraining `<END>` (257) doubles as the SFT end-of-response target/stop.
- **SFT dataset (`sft.rs`).** Reads a JSONL in either of two shapes (dependency-free string parser — no serde), one window per record. A dolly record (`{instruction, context, response, category}`) becomes `{instruction}[<CONTEXT>{context}]<SEP>{response}<END>`. A record carrying a `messages` array (`{"role", "content"}`, the OpenAI/LM-Studio shape) becomes a **conversation** — `user₁<SEP>asst₁<END>user₂<SEP>asst₂<END>…` — where every assistant turn carries loss and every user turn does not; a `system` message takes the `<CONTEXT>` slot of the first turn, so multi-turn needs no new vocab and no checkpoint surgery. A `tool` message is what a call returned: prompt-side like a user turn, so the model is trained to *read* a result and answer from it (`<tool>lamp.set(on=true)</tool><END><result>already_on</result><SEP>It's already on.<END>`) rather than to invent one. An `assistant_context` message is an assistant turn laid out exactly like a normal one, `<END>` included, that records **no loss span** — so a conversation can contain a wrong tool call the model then recovers from, and only the recovery is trained. That is the whole mechanism for error handling: the mistake is context the backbone reads, never an output any gradient pushes it towards. A `no_loss` array on a message (`[[start, end], …]`, byte ranges of `content`) is the same thing at **sub-turn** resolution: `mask_pieces` cuts the turn at those borders, writes every piece and records a loss span only for the trained ones, so one answer can hold a wrong call and its correction while only the correction is learned. `<END>` joins the loss whenever any part of the turn does; a fully masked turn is exactly `assistant_context` (pinned by a test). Ranges are normalized, not trusted — unordered, overlapping, past the end or inside a multi-byte character all round out safely, and the segmentation rounds a border to the word border, which is the unit the mask is applied in. `parse_messages`/`build_example_turns` handle the second shape, `segment_with_spans` builds the multi-span mask, and `load_jsonl` picks the shape per line. Both mask paths downstream (CPU `dec_word_loss`, GPU `forward_backward_masked`) are already per-word, so several loss spans need nothing new. `segment::word_ends` already makes each special token its own one-token word, so the per-word **loss mask** is a clean flag: words at/after the response carry loss (`true`), the prompt (through `<SEP>`) does not. The whole sequence is still encoded/decoded — the backbone must read the prompt — but gradient flows only from the response. Examples longer than `SFT_MAX_TOKENS` (4096) are dropped at load: the per-example cache is sized to one slot per token, so dolly's ~27k-token tail would otherwise force a ~16 GB cache (~2.4 GB at 4096) and OOM before the first step. `datamix`'s `trim_turns` keeps a long conversation's leading exchanges instead of dropping it — at 2048 that was the difference between 35% and 82% of SmolTalk.
- **Training — two paths, same masking.** Both load the whole (small) SFT set into memory, shuffle per epoch, reject a stale-vocab checkpoint, and fine-tune at `SFT_LR` (1e-5, ×10 below pretraining) over `SFT_EPOCHS`.
  - **GPU (`train_sft_gpu`, mode `hqg`)** calls `gpu::Hierarchical::forward_backward_masked`, which mirrors `forward_backward` but takes a per-decoded-word mask (`word_loss[w]` gates the CE mask of every decoder slot of word `w+1`) and normalizes the loss by the **unmasked** row count.
  - **CPU (`train_sft`, mode `hq`)** calls `cpu::Hierarchical::forward_backward_masked`, the same per-word mask and normalization: a masked word's decoder group is not run at all. `cpu/hierarchical.rs` pins it — a fully-masked window gives exactly zero gradient everywhere, and the one-word masks, weighted by their share of the rows, sum to the full-window gradient (masking is additive and isolating).
- **Inference (`sample_chat`, mode `hqs`).** A multi-turn REPL: it keeps the conversation as `Vec<Turn>`, formats it with `sft::format_chat_prompt` (every completed exchange, then the pending user turn and its `<SEP>`), encodes the *whole* prompt into the backbone (nothing teacher-forced, unlike `sample`), generates until `<END>`, and appends the reply as an assistant turn. A reply containing `<tool>` is not an answer but a request for a result: the REPL prompts for one, appends it as a `Role::Tool` turn and generates again, up to `MAX_TOOL_ROUNDS` — which is what lets `app.launch` → `not_found` → `app.list` → `app.launch` play out. Context is asked once per conversation and lands in the `<CONTEXT>` slot; `new` clears the history. `sft::format_prompt` remains the single-turn form.

### Dataset mixing (`datamix/`, `mixes/`)

`datamix` is a workspace member (CPU-only, `default-features = false` on the parent crate) that builds the corpora the trainers read. A **mixture file** (`mixes/*.toml`) names the sources, their weights and the quality gates; nothing is compiled in. The format is TOML, parsed by `datamix/src/toml.rs` — a hand-written subset (tables incl. dotted/quoted names, basic and literal strings with their multi-line forms, integers, floats, booleans, arrays; no inline tables, arrays of tables or dates), because the repo carries no serde. The point of TOML here is tooling: `datamix/mixture.schema.json` (named by a `#:schema` line in each mixture, and wired up in `.vscode/settings.json`) gives key completion and unknown-key warnings in the editor, and `config.rs` re-checks the same things — unknown key, unknown table, wrong type — with `file:line` at build time. `config::tests::the_shipped_mixtures_parse` pins the shipped files, including that their wrapped prompts join into flowing text.

```bash
cargo build -p datamix --release
./target/release/datamix check  mixes/pretrain.toml        # stats only
./target/release/datamix sample mixes/assistant_sft.toml -n 8
./target/release/datamix build  mixes/assistant_sft.toml
./target/release/datamix verify data/mix/assistant.jsonl # loads it via sft::load_jsonl
./target/release/datamix synth  mixes/synth/apps.syn -n 10
./target/release/datamix edit   data/sources/handmade.jsonl    # browser UI, port 7878
```

`datamix edit` is the hand-writing path: a loopback HTTP server (`datamix/src/editor.rs`, no dependencies) serving one page (`editor.html`) that reads and writes the JSONL directly, so a hand-written corpus is a plain `kind = "jsonl"` source like any other. The page does all JSON escaping itself (`JSON.stringify`), so a newline or a quote typed into a turn is simply typed. Each record is a conversation of role-tagged turns or a single dolly-style pair; below the turns it renders the **wire form** — the same assembly `build_conversation` does, `<CONTEXT>`/`<SEP>`/`<result>`/`<END>` in place, whitespace optionally shown as `·`/`¶` — with the loss-carrying spans highlighted, so what the mask covers is visible rather than inferred. Masking is two gestures: a **"train on this" checkbox** on each assistant turn (off writes it as `assistant_context`), and, inside a turn, selecting text and pressing *don't train selection*, which writes a `no_loss` range — the selection is snapped out to word borders first, so what is shown highlighted is what is actually trained. Masked ranges appear as struck-through chips under the turn (click to train it again) and follow the text when it is edited. Saving writes through a temp file and then loads the result with `sft::load_jsonl`, so the status line is the training loader's own verdict.

A build runs in two passes: every source streams through its filters into a staging shard under `target/datamix-stage` (so memory is bounded by one record, not by the corpus), then the mixer draws each source's shuffled records until it has covered its share of the budget. `weight` is a share of the output, counted in the unit `[output] weight_by` names — `tokens` (budget `tokens`) or `records` (budget `records`), one example counting as one whatever its length. On an SFT mix the unit decides the corpus: a tool call is a handful of tokens and a chat conversation is thousands, so a source at 12% of the tokens is most of the questions (`mixes/assistant_qa.toml` is the record-weighted SmolTalk mix, ~1.7% tool calls). `epochs` caps how often a source may repeat. With no explicit `tokens` budget the corpus grows until the first source would exceed its `epochs` — that binding source is named on stdout, because it sets the size of everything. With an explicit budget, any source that cannot fill its share is reported the same way (stdout plus a `capped` column in the report): what it asked for, what its `epochs` allowed, and how far short of the budget that left the corpus.

Output kinds are `sft` (JSONL: dolly-layout records, or `{"messages": [...]}` conversations for multi-turn — both what `hqg`/`src/sft.rs` reads), `text` (`<|endoftext|>`-separated, what `ChunkedWordDataSet` reads — the separator is consumed by its `split` and replaced with the `<END>` token, which is masked out of the loss and exists only to key the state reset) and `none` (report only). Input kinds are `file`, `dir`, `parquet` (via `src/parquet.rs`, with the same `language` column filtering), `chat`, `dolly`, `jsonl`, `synth` and `llm`. `chat` reads a parquet whose messages column is a `list<struct<role, content>>` — SmolTalk and every other HF chat corpus — one `Record::Chat` per row; `select_column`/`select_values` keep only the rows whose flat subset column matches (and `where = ["category!=role-playing", "quality!=poor|very poor"]` adds any number of further conditions on flat columns), which is what lets one corpus be split into several weighted sources (SmolTalk's subsets differ by 10x in answer length, so taken whole its longest subset sets the model's register). A `dir` path — or a `parquet` path naming a directory — reads every matching file in sorted order, with `skip_files`/`max_files` cutting the listing down (that is how a sharded corpus already half-trained-on is resumed).

Filters are inherited from `[filter]` and overridable per source: size and token caps, `min_alpha_ratio`, `max_line_bytes`, `max_dup_line_ratio`, substring allow/blocklists (`must_not_contain` over the whole record; `user_`/`assistant_`/`system_must_not_contain` over one role's turns, where a leading `^` anchors at the turn start — `"^you are a"` is a roleplay setup, `"if you are a US citizen"` is not), `dedup = off|exact|near` (near = MinHash over word 5-grams; on short formulaic SFT records prefer `exact` — `near` reads two commands differing only in the room as one), and `judge` (see below). A `transform` prompt goes one step further and rewrites each record instead of only vetting it: the record travels as `{"messages": [...]}` and must come back with the same turns, in the same order, with the same roles — a reply that drops or relabels one is refused (`rewrite failed` in the report), because a relabelled assistant turn would move the SFT loss mask onto the prompt. `verify = "rust"` then compiles the ```rust blocks the rewrite produced and drops what does not build, giving it one repair pass with `rustc`'s own errors in hand first (measured 63% -> 79%; a second pass adds nothing), and `system_strip` cuts the identity boilerplate out of system turns before any of it — twelve strings cover 32% of `assistant_qa`'s records, a constant the model learns to lean on and never sees at inference, while `system_fold` optionally moves the surviving instruction into the user turn (the turn cannot simply be deleted: in ~23k records it is the only instruction there is). `transform_when` gates which records are sent at all, and the reply is cached on the record's own text (under `data/llm-cache` — outside `target/`, because a ~56 h rewrite is not a build artifact and `cargo clean` used to take it), so the rewrite survives a rebuild. `transform_only = true` goes one step further and drops everything `transform_when` did *not* match, which turns a rewrite into a corpus of its own: `mixes/rustified.toml` is that mixture (`cache_only`, so it opens no socket) and it writes SmolTalk's translated Python half to `data/sources/rustified.jsonl`, which every SFT mixture then reads as a plain `kind = "dolly"` source instead of carrying its own copy of the rewrite prompt. `mixes/assistant_qa.toml` reads it that way and blocklists the Python markers, so an untranslated original cannot come in beside the translation. Every rejection is counted by reason and printed in the report — `data/rust-lib` is 97.7% byte-identical duplicates (1.2k unique files of 62.8k), which only the report makes visible. An unknown key is an error naming the line.

A **local OpenAI-compatible server** (LM Studio's `http://localhost:1234/v1`, configured in `[llm]`) does two optional jobs, both opt-in — a mixture using neither never opens a socket. `kind = llm` sources generate examples: the reply is read as JSONL (one `{instruction, context, response}` per line, or one `{"messages": [...]}` conversation, `<think>` preludes and code fences stripped), and `seed_file` renders `seeds` examples into `{seed}` per call **through the same `mix::render` the writer uses**, so the model sees the exact output format. That sharing is load-bearing: seeded with bare instructions, a local 20B model invented `turn_lights_off(room='dining room')` instead of the corpus's `<tool>lamp.set(...)</tool>`. A `judge` prompt (in `[filter]` or one source) vets each surviving record — the reply must start with `judge_expect` (default `yes`) — and shows up in the report like any other filter. The judge runs at `judge_temperature` (default **0**, not the generator's temperature) and optionally `judge_model`: measured on 10 generated tool calls, the same judge kept a malformed invented-tool example at temperature 1.0 and rejected it at 0. A judge prompt that names the exact tools, arguments and allowed values catches far more than a general one. Every completion is cached under `data/llm-cache` keyed on model/temperature/prompt/call index, so a rebuild makes no calls. `datamix ping [mix.toml]` checks the server. The HTTP client is hand-rolled over `TcpStream` (`datamix/src/llm.rs`): one POST with `Connection: close`, http only, every resolved address tried (localhost resolves to ::1 first). `[llm] workers` sets how many requests are in flight — for the rewrite and, since generation is the same kind of wait, for `kind = llm` sources too (one generation call is ~100 s of a 27B writing six conversations, and asking for them one at a time left seven of eight slots idle: 2.8 records/min serial against 16 in rounds of eight). Match the server's parallel slot count. The judging that follows each round stays serial, because the shard is written in order, and `completion_template` writes the chat template out, switching every call to `/v1/completions` — the only way to prefill the assistant turn, which is the only way to stop a reasoning model deliberating (LM Studio ignores `chat_template_kwargs`, `/no_think` and `reasoning.enabled` alike). Prefilling an empty `<think></think>` measured 4.3 s against 43.6 s per rewrite with no quality loss; the template is part of the cache key.

`synth` sources expand template files (`mixes/synth/*.syn`) into instruction data for skills no public corpus covers (the lamp, app launching, the assistant's own identity): a template with `user =` / `assistant =` lines produces a multi-turn conversation whose lists bind once per example, so a later turn can refer back to what the first one named, a `tool =` line is what the call returned — the reply after it is what the model is trained to write — and an `assistant_context =` line is a turn the model reads but is never trained to produce, which is how the error-recovery templates put a wrong call in front of the correction without teaching the wrong call (`mixes/synth/lamp.syn`, `apps.syn`, `math.syn`, `tools_in_context.syn`, `persona.syn`); `list` entries carry `;`-separated fields so the spoken form (`{room.0}`) and the tool identifier (`{room.1}`) stay bound to the same entry, and `{a|b|c}` is an inline paraphrase drawn per example (never trimmed, so `{|s}` writes an optional word). The tool-call syntax in the responses is a convention of the data alone — whatever parses it downstream must agree with those files. See `datamix/README.md`.

The tool surface those files define is seven calls: `lamp.set(on=…)`, `lamp.state()`, `app.launch(name=…)`, `app.list()`, `browser.open(url=…)`, `media.control(action=…)` and `math.eval(expr=…)`. Nothing in this repo implements any of them — the surface is a convention of the data, so it must match whatever parses `<tool>` downstream, and a call the runtime cannot answer is the same defect as an invented one. The runtime that answers them is `harness` (`../harness/src/tools/`), where `math.eval` lives in `math.rs`: an infix evaluator whose errors name the character the repair strips, pinned by tests against `math.syn`'s own `slip` list. `system.screenshot()` and `app.quit(name=…)` were in the corpus and are not implemented, so they were cut and moved into `no_tool_var` as requests to decline; they are the sharpest cases there, because both sound exactly like something the assistant can do. **Applications are not a fixed set**: `mixes/synth/apps.syn` is generated by `scripts/gen_apps_syn.py` from `datamix/pools/installed_apps.json` (this machine's real `.desktop` ids plus a general pool), drawing a fresh `app.list()` answer for every example — 177 distinct lists in 371 records, 145 distinct ids, lengths 6 to 46. The hand-written version it replaced had one seven-id list that appeared in 24 of 25 examples, so the model would have learned `app.list()` as a constant to recall rather than a list to read, and it never emitted a reverse-DNS id at all while 33 of this machine's 86 apps are shaped `org.kde.dolphin`. The policy the data teaches follows from that: launch directly when the spoken name is a plausible id, let a wrong guess come back `not_found` and let the list decide, and call `app.list()` **first** when the request is a description ("the file manager") because there is nothing to guess from. `math.eval` takes one **infix expression as a string** (`"87.40 / 3"`), operators `+ - * / ^` with parentheses and `sqrt/abs/min/max/round/floor/ceil`, and nothing else — no currency symbol, no percent sign, no thousands separator, no unit and no word, so translating the request into bare arithmetic is the assistant's job and the units live in the sentence it writes afterwards. The alternatives were worse for a small model: per-operation tools (`math.add(a, b)`) turn `(87.40 - 12) / 3` into three chained calls and three chances to drop a number, while an RPN or JSON-AST argument is a syntax the pretraining corpus never contains, so it would have to be learned from the SFT data alone. Infix in a quoted string is already everywhere in pretraining and is the same `name="…"` shape as `app.launch`.

**`mixes/assistant_full.toml`** is the full-size SFT corpus: all of SmolTalk that survives the filters (minus `systemchats`, `apigen`, the all-Python `self-oss-instruct` and the over-long `longalign`), plus no_robots and oasst2, each source taken whole and once (weight = its kept count) — 757k records, 2.69G tokens. It carries no persona source and filters out every record that teaches a different identity or a roleplay. The raw corpora sit unfiltered under `~/training_data` (`scripts/fetch_sft_data.sh`), so a filter change is a rebuild, never a re-download.

**`mixes/tools.toml`** builds the tool-calling corpus on its own, into `data/sources/tools.jsonl`, which the SFT mixtures read as a file. The `.syn` files are its floor — they guarantee every tool, argument and result string appears in the exact wire syntax — and five `kind = "llm"` sources supply what a template cannot: `length_var` (one-to-three-word commands and 80-250 word rambles with one request buried in them, because a template's user turn is always a four-to-nine word imperative and a model trained only on those answers anything else in prose), `buried_var` (the call arriving under a filled system context or mid-conversation, never in turn one), `recovery_var` (the first call is wrong and is written as an `assistant_context` turn, so the mistake is read and never trained), `math_var` (arithmetic that arrives as a life question rather than as a sum) and `no_tool_var` (requests that sound like tool requests and have none — a brightness on the one lamp, a thermostat, a timer — which is what stops a generalising model inventing a plausible call). Every generated record is judged at temperature 0. Two things were measured while tuning that judge: a **long checklist is the wrong shape for a one-token verdict** — the same records come back yes or no depending on how much of the list the model still holds — and with the empty `<think>` prefill there is nowhere for the decision to happen at all, so a one-word answer collapses onto "no" (96% rejection on records the same judge accepts as soon as it may name the bullet). Both are fixed the same way: six bullets, and the **verdict first, then a dash and the clause that decided it** — `judge_expect` matches the start of the reply, so the reason costs nothing. The bullets cover only what would poison the corpus (an invented tool or argument, a `tool` turn holding something that is not a real result string, an outcome the tool never reported, wrong arithmetic); tone, length and how interesting a record is are left to the generator prompt.

### Dataset (`src/batches.rs`)

Both training modes stream `TRAIN_DATA` through `ChunkedWordDataSet`, which reads roughly `CHUNK_BYTES` of raw text at a time and tokenizes + word-windows it into a `WordChunk`. The raw documents come from a `TextSource`, picked by file extension:

- **text** (anything but `.parquet`) — a single file with `<|endoftext|>` document separators; each read is cut at the last complete document and the partial tail is carried into the next chunk.
- **`.parquet`** — one row per document, read from the `text` column (override with the `PARQUET_TEXT_COLUMN` env var). Row groups are already document-aligned, so there is no separator scanning and no carry; a chunk is however many row groups it takes to reach `CHUNK_BYTES`.

`config::ALLOWED_LANGUAGES` filters a parquet corpus by its `language` column (`PARQUET_LANGUAGE_COLUMN`): rows whose ISO code is not listed are dropped *before* tokenizing, which is the expensive part. The language column decodes alongside the text in the same row group, so the two stay row-aligned. An empty list disables filtering; a corpus lacking the column is read unfiltered with a printed note rather than failing, and plain-text corpora are never filtered (no per-document language exists). Filtering out an entire row group is not end-of-corpus — the loader keeps advancing until the row groups actually run out.

Both hand the loader the same thing — a batch of *complete* documents.

**Packing.** A chunk's documents are concatenated into one token stream, each closed by an `<END>` token, and the windows are cut from that stream. A window is therefore `WORDS_PER_SEQ` words whatever the documents in it are long, instead of ending wherever the document did — on `pretrain_v2` that is 4094 words per window against 1046 before, so a window covers 3.9x the corpus it used to and every word carries the same weight in the loss (the CE is normalized per window, so under variable window sizes a word in a short document counted for up to 40x one in a long document). Consecutive windows **overlap by one word**: a window's last word is a decode target only (the backbone stops one short of it, since nothing after it is predicted in this window), so edge-to-edge windows would leave the prediction across every border untrained. With the overlap the windows partition the stream's backbone steps and its predictions, and `WordBatch::continues` marks each one that resumes the previous — which is now every window but a chunk's first. `CARRY_WINDOW_STATE` (config, on) makes the GPU pretrainer act on it (`Hierarchical::set_stateful` + `set_continues`): the state crosses the window border, the gradient stops at the window's own first word — truncated BPTT, the same truncation `BACKBONE_CHUNK` already imposes inside a window. So a chunk is autoregressed as one long sequence. `carried_window_decodes_like_one_long_window` pins the second window's loss against a masked whole-window run.

**Document borders.** `WordBatch::doc_starts` gives the word indices where a document begins inside the window — offsets, so the list ends with the word count and a window closing on an `<END>` still finds the start one past it. `Hierarchical::set_doc_starts` (both the GPU model and the CPU twin) is what the trainer hands them to, and two things follow. First, every backbone cell restarts its recurrence at the border row, in place: `backbone_spans` hands each `BACKBONE_CHUNK` span the document starts inside it (`Resets`, a host row list plus a device `i32` mask), and the chunks themselves ignore documents — cutting a span at every border used to run ~12 spans per window instead of 8, each through all 28 blocks, and in-kernel resets measured 6% faster per window (`gpu_soak`, 0.483 vs 0.513 s). The sLSTM restart is exact: the fused and per-step loops run a reset row as a sequence's first (zero state, no recurrent `h·Wh` half), and in backward nothing crosses it towards the row before. The mLSTM follows NX-AI (`reset_fgate_value` in xlstm-jax): the forget-gate logit of the border row is overwritten with `DOC_RESET_FGATE` after the gate projection and its gradient zeroed before the projection's backward, so the arriving state decays by `σ(−100)`. Not their −25 — theirs sits behind a ±15 gate soft cap we do not have, and `document_reset_survives_a_saturated_stabilizer` shows −25 leaking half the output scale once the stabilizer ends a document far above the next row's `ĩ`. −100 cannot overflow (every `expf` in the kernels takes a stabilizer-bounded difference); its cost is ~1e-5 in the log-forget cumsum of the rows after the border within its 32-row chunk. Second, the two words at a border carry **no loss**: the document's first word, whose only available context is the last step of the document before it, and the `<END>` closing that document — a marker the reset is keyed on, not text anything should learn to emit. That costs 0.183% of all predictions on `pretrain_v2` (3.74 borders per window). `packed_document_decodes_like_its_own_window` pins that a packed document decodes exactly as it would in a window of its own, with the border left undeclared as the control and the border mask spelled out by hand as a third leg. Resets also happen at a chunk border of the loader and wherever a resume starts mid-file, so nothing inherits a document it did not run; SFT stays unpacked and stateless. `examples/win_carry_stats.rs` reports the shape of a shard.

Packing makes the chunk cuts part of the windowing: which documents share a window depends on `CHUNK_BYTES`, so a given chunk size is reproducible but two different ones do not agree, and a corpus's window count changed when packing landed (an older `.pretrainprog` sidecar fails its `windows` check and restarts the current file).

`src/parquet.rs` is a dependency-free reader covering just the slice of the format these corpora use: flat schema, one BYTE_ARRAY column, REQUIRED or OPTIONAL (nulls skipped), UNCOMPRESSED/SNAPPY, data pages v1 and v2, PLAIN and dictionary encodings, RLE definition levels. Anything outside that returns an `Err` naming what it hit rather than silently decoding garbage. `cargo run --release --example parquet_demo -- <file.parquet> [column] [--all]` dumps row/group counts, the first documents, and decode throughput (`--all` streams the whole file — the end-to-end check for a new corpus). Peak memory is bounded by `CHUNK_BYTES`, not corpus size (>1 GB corpora stream fine). Training loops call `rewind()` per epoch and grow the model cache on demand when a chunk's `max_window_tokens()` exceeds the current size; `count_windows()` does a cheap counting pass for resume arithmetic.
